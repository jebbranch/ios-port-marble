# apps-smmu（marble / SM7475）：已经证伪的路，别重走

> 写给下一个接手的人。这里每条都对应真机实验（run 号在括号里），
> 不是推测。**看到「寄存器能读能写」不要当成「这条路通了」。**
>
> **★ 2026-10-27 修正（先读这条）：下面「停止 apps-smmu 路线」的结论作废。**
> 挂死的真正原因不是 hypervisor：厂商的 `SHM_MAP` 地址高 32 位是 **1**
> （stream index），我们一直发 0。加上 `sweetshmhi=1` 之后，同一套 S1 配置
> **不再挂总线**，控制面全部 status 0。细节和剩余缺口见
> [`audio-closeout.md`](audio-closeout.md)。本文档里的寄存器值和实验记录仍然有效，
> 但不要再据此认为"AP 不可能让 DSP 读主存"。

## 0. 正确的寄存器地图（4 KiB 寄存器页）

`ID1 = 0x6000004b` 的 `PAGESIZE` 位 = 0 ⇒ 页移位 12 ⇒ **GR1 = base + 0x1000**。

| 寄存器 | 地址 |
|---|---|
| GR0 | `0x15000000` |
| GR1 | `0x15001000` |
| `SMR(n)` | GR0 + `0x800 + 4n` |
| `S2CR(n)` | GR0 + `0xC00 + 4n` |
| `CBAR(n)` | GR0 + `0x1000 + 4n` |
| `CBA2R(n)` | GR1 + `0x800 + 4n` = base + `0x1800 + 4n` |
| `CBFRSYNRA(n)` | GR1 + `0x400 + 4n` |
| CB 页 | `0x15080000 + 0x1000n`：SCTLR +0x00、TCR2 +0x10、TTBR0 +0x20、TTBR1 +0x28、TCR +0x30、MAIR +0x38、PAR +0x50、ATS1PR +0x800、ATSR +0x8F0 |

⚠️ **`base + 0x8000` 不是 GR1**（那是 AArch64 SMMUv3 的页面偏移）。
v79/v80 按 0x8000 写过 CBA2R，**当场 panic**（外部中止）。v82 已回退。
`base + 0x2000` 是实现定义区，读写不中止，但也不是 GR1。

## 1. 已证伪

| 尝试 | 结果 | 证据 |
|---|---|---|
| `S2CR = 0x10000`（BYPASS） | 回读变成 `0x20000`（FAULT），有人在我们之上改写 | run71/73 |
| `S2CR` 指向 bootloader 已有的 CB3 | 挂死 | run75 |
| 自建 CB52 + 两级页表（回读全对） | 挂死 | run81 |
| 引到 stage-2 bypass 的 CB0 | 挂死 | run88 |
| `SMR` 写 SID `0x1800` 或 `0x1802..0x180f` | **写即总线中止** | run70/103/105 |
| `SMR` 带任何 MASK≠0 | 写即总线中止 | run69/82 |
| `CBAR(6)` / `CBAR(52)` 写 | 外部中止 | run77/79/80 |
| 用**真实物理地址**代替 IOVA 填 SHM_MAP | 同样挂死 | p1/p2 |
| 用 vendor 的 4 子图图定义走共享内存 open | 一发出就挂死 | o2/o3/o4 |

**四条互不相同的 SMMU 配置表现完全一样 ⇒ 卡点大概率不在我们写的寄存器值上。**

## 2. 已经从原厂抓到的"标准答案"

在跑 Android 的内核上挂 kprobe（开机 11 s 就挂，`msm-audio-ion` 在 13.4 s
attach），拿到的是厂商驱动**真实写进硬件**的值：

```
SMR   = 0x80001801   (VALID | SID 0x1801, mask 0)
S2CR  = 0x34         (type = S1 translate, cbndx 0x34)
CB    = 0x34，CBA2R 写在 base+0x18d0 = GR1+0x800+4*0x34
IOVA  : 0x1FFD8000 / 0x1FFF0000，size 0x5000，池 = 0x10000000..0x20000000
fault : Android 全程 0 次
```

**我们复刻了这三项（SMR/S2CR/CB 索引完全一致），DSP 仍然在第一次读主存时
把总线打死。** 这是"我们写错了"这个假设最有力的反证。

## 3. 还没做、值得做的判定（做完就该下结论）

1. **ATS1PR 自检**（纯 AP 侧，不碰 DSP，不会挂机）：
   向 **实际映射的 IOVA**（`0x1FFE8000`）发翻译请求，读 PAR。
   低级位 = fault。返回 `0xa2fe8000` 且无 fault ⇒ 我们的 S1 表是对的。
   ⚠️ 早期版本探的是 `0xa2e00000` / `0x10000000`——两个都没映射，
   `par=0` 是正确结果，**不能**当成失败证据。
2. **换 CB 0x34**（`sweets1cb=52`）：和原厂同一个 context bank，
   排除"CB5 不属于我们"这个变量。
3. **CBFRSYNRA(n)**（GR1+0x400+4n）：S2CR 里那个 `0x34` 还带着别的位，
   如果 SID 的 fault 落在这里，说明命中根本没走到我们配的 CB。

## 4. 纪律

* **不要用 DATA_BUFFER 当探针。** 它会打死整机总线，把同一轮里其它线索
  一起带走。先用 ATS1PR / CBFRSYNRA 这类不惊动 DSP 的手段。
* **日志的截断点 ≠ 崩溃点。** `printf` 之后没有 `sweet_log_sync()` 的行
  会留在缓冲里丢掉。判断位置要看最后一个**带 sync** 的输出。
* **`base+0x2000` 可写** 不代表它是 GR1；**寄存器回读一致** 不代表
  这个 context bank 归你。

## 5. 2026-10-27 终局判定（v82）

| 运行 | 配置 | 结果 |
|---|---|---|
| s1 | CB5（bootloader 的 S1 银行） | `cba2r=1` ✓、`cbar=0x1f000`（type=1）✓、**DSP 仍挂死** |
| s2 | **CB 0x34**（Android 同款），写 CBAR=0x10000 | `cba2r=1` ✓、`cbar=0x10000` **写入成功**（推翻旧笔记“CBAR(52) 写即中止”）、**DSP 仍挂死** |

* `SMR=0x80001801`、`S2CR=0x34`、`CBA2R.VA64=1`、`CBAR.type=1` 全部与原厂一致，
  仍然死 ⇒ **不是我们寄存器写错**。
* `ATS1PR` 自检**无效**：探映射 IOVA 和"未映射 IOVA + 2 MiB"返回的 PAR **都是 0**。
  正确的翻译应返回 `0xa2fe8000`，未映射应置 fault 位；两个都 0 说明这个
  请求根本没产生结果（ATS 未完成/不支持/PAR 偏移不对），不能当通过。
  ⚠️ 之前的打印把 bit0=0 标成 "OK"，会误导读日志的人——**par=0 是"没结果"**。
* CB52 的 `TCR2=0x24071` 是残留值（CB5 是 0x60）。如果要继续走 S1，
  应该显式写 TCR2=0；但这不改变上面的结论。

**结论：停止"由 XNU 手工接管 apps-smmu 翻译型数据路径"这条路线。**
证据见上：原厂三项配置全复刻、两家 context bank 都试、VA64 已置位，
DSP 依然在第一次读主存时打死总线；而 BYPASS 被 hypervisor 改写为 FAULT，
连"绕开翻译"的开关都拿不到。
