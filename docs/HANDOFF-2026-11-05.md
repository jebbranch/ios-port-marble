## 三、已关门的轴（不要再花开机）

1. **地址 / 地址形式 / 是否在声明区间内**（E、F）：`0x1000`/`0x3000`、bare/region-base+offset、越界 `0x6000` 全回同码。
2. **正文字节**（J）：真实 ACDB 字节与全零同码。
3. **传输（带内 vs 带外）与总长度**（L1 288 B 带内、L2 216 B 带内）：与带外同码。
4. **记录编码 framing**：我们那份被接受的 344 B `GRAPH_OPEN` 正文与被拒的 `SET_CFG` 容器
   **同用 16 字节 `apm_module_param_data_t{iid,param_size,error_code}` + align8**；
   五个头在 `0x000/0x040/0x0b8/0x0e8/0x130`，size `48/100/32/52/20` ⇒ `5×16+264=344` 闭合。
   复核命令：`python3 tools/walk_param_records.py`（我曾把这份正文误读成"ACDB 链式 8 字节头、无 iid"，已两处更正）。
5. **逐记录 `error_code`**（N1）：带外侧实测**没人写**（哨兵原样、288 B 一字节未变），
   头文件也写明该字段 *"Applicable only for out-of-band command mode"*，而命令级应答只有 32 B、装不下四条码。
   ⇒ **记录级拒绝原因在当前协议形态下不可观察。**
6. **`iid` 作为 `0x1`↔`0x3` 的分界**：作废。`(iid=0x428f, param=0x08001004)` 在 I 的 9 条容器里是 `0x1`、
   在 M1 的 2 条容器里是 `0x3`；`iid=1` 只在 `0x3` 那一侧出现，是**单向事实**不是规则。

## 九、外设另两条线的取证（2026-11-05 深夜，全部零开机）

用户问"基带能不能啃""那 wifi 呢"。取证结论放在这里，免得下个会话重新摸。

### 基带（modem / MSS）
- **仓库里没有任何基带工作**（干净负结果）：没有 modem 驱动、没有 MSS/PAS 调用、磁盘上没有 modem 固件。
  唯一一行 modem 字样是**误打误撞**：`xnu/patches/0139-sweet-low-shared-probes.patch:12` 的
  `g_apm_map_probe(0x8bbe0000, …, "spu_modem")` —— 那是**拿 ADSP 的 SMMU 去探 SPU-modem 预留区**，
  0140 就删掉了，而且 0136–0139 整批探的是**错地址**（真正厂商 PA 是 `0x1_1FFE8000`，msw=1；
  见 `docs/status-log.md:263` 与 `:327` 的更正）。
  陷阱记账：**`sweetnobb` 是 "no bit-bang"（0241），跟基带无关**；`mkadt.py:161` 那句
  *"no SEP, no baseband here"* 说的是**这台机器上跑 iOS 没有 SEP/BB 资产**，不等于"modem 起不来"。
- **AGENTS §7 里没有基带的"不要重走"条目**；唯一红线是"不碰 GPT / persist / modemst"（`AGENTS.md:19`）。
- **机器实况**（Android 正在跑，读只读）：`4080000.remoteproc-mss`，`firmware=modem.mdt`，`state=running`；
  `dmesg-after-4320.txt:11159` "Booting fw image modem.mdt, size 6364"，`gsm.version.baseband = MPSS.DE.2.0.c1-CN`。
  固件 = `/vendor/firmware_mnt/image/modem.{mdt,b00…b34}`，**35 个文件 ≈104 MB**；分区 `modem_a → sde7`。
- **DT 证据**（`logs/fdt/marble-live.dts`）：`:9272` `remoteproc-mss` = `qcom,cape-modem-pas`、`status="ok"`；
  **`memory-region` → `mpss_region@8bc00000`，size `0x13200000` = 306 MB**（`:144`）——
  这是这条线最大的单个新数字：ADSP 当年我们用的是 `0x9fd00000 + 0x3100000`（49 MB），
  **MSS 要的是一块大三倍多的预留区**，先核 XNU 侧能不能拿到它（reserved-memory 在我们启动时是否还空着）
  再谈鉴权。其余依赖：`xo` 时钟、`cx/mx` 轨、`rproc_ddr`/`crypto_ddr` 互连、六个 PIL 中断、
  `qcom,smem-state "stop"`、`:9815 smp2p-modem`、`:10145` memshare 客户端、`:9619 microdump_modem`。
- **传输与我们的重合度高**：`:9290` `glink-edge` ⇒ `transport="smem"`、`label="modem"`、
  `qcom,glink-label="mpss"`，子节点 `qcom,modem_qrtr`（通道 **`IPCRTR`**，intents `0x800×5, 0x2000×3, 0x4400×2`）
  与 `qcom,modem_ds`（`DS`）。`sweet_glink.c` 已经是 GLINK-over-SMEM 客户端 + GPR 路由 ⇒
  **可复用件**：`sweet_adsp.c` 的 `pas_init_image/pas_mem_setup/pas_auth_and_reset`（只差 PAS ID 与区域）、
  0109 的 SCM 能力探针（已证明 `pas_auth_and_reset`/`pas_shutdown` 在 TZ 里可用）、
  `g_apm_shm_map_*`/`g_smmu_faults`/`g_prm_vote_clock_ex`、PSCI `smc #0`。
  **缺件**：`scripts/extract_adsp_fw.sh` 是 **`adsp2.*` 写死的**，modem 没有对应脚本，而且 modem 固件在
  `/vendor/firmware_mnt/image`（= `modem_a`）而不是 `/vendor/firmware`；`mkfwblob.py` 是前缀参数化的，能改。
- **更正我自己上一条关于 MHI 的话**：`mhi_1103_*`（DIAG/IPCR/LOOPBACK）**不是基带的，是 WiFi 芯片 CNSS 的**
  （`dmesg:4621 pci 0000:01:00.0 [17cb:1103]`；DT `:10168 mhi_qrtr_cnss = "qcom,qrtr-mhi"` dev-id 0x1103）。
  ⇒ 基带只有 **MSS/PIL + GLINK/SMEM + SMP2P** 一条路，没有 MHI 第二条。`dmesg:2297` 还有一句
  "PCIe: RC0: no mhi resource found"，别把它误读成基带缺资源。

### WiFi（CNSS / QCA6490）
- 芯片 = **外挂 PCIe 的 QCA6490**：`PCI_ID=17CB:1103`，`DRIVER=cnss_pci`，挂在 `qcom,pcie@1c00000`
  （DT `:16384`，`perst-gpio` TLMM 0x5e，`qcom,pcie-phy-ver=<0x63>`）。
- 资产在 `/vendor/firmware_mnt/image/qca6490/`，**26 MB**：`amss.bin`/`amss20.bin`（5.3 MB 设备镜像）
  + `Data.msc`/`Data20.msc` + **板级数据多变体** `bd_l1.elf / bd_l10.elf / bd_l10gf.elf …`、`bdwlan.e01…e06`
  ⇒ "写完整套驱动却因为选错 bdwlan 变体而连不上"是这类的经典坑，**先零开机确认本机用哪一个**。
- 另有 `/vendor/firmware/wlanmdsp.otaupdate` ⇒ **WLAN 自带一颗 DSP**，要再走一次 PAS 鉴权。
- 依赖比基带多而重：5 条电源轨（aon/dig/io/rfa1/rfa2 + 天线开关，各带电压配置）、`wlan-en-gpio` +
  active/sleep 两套 pinctrl、**PDC**（`:5869 qcom,pdc`,`qcom,cape-pdc`）、`cnss_wlan_region`、
  `ipa_smmu_wlan`（WiFi 数据面走 IPA offload）。
- **判断（可与用户讨论，非定论）**：WiFi 比基带贵，因为它要新长四段——PCIe RC/PHY 链路（本项目从没做过，
  GPU 是内置不占这条）、MHI 主机栈、**整套 802.11 驱动**（QCA6490 属 M3/`ath11k` 那一类：HTT/WMI/HAL ring +
  DP 缓冲 + 板级 cal），外加用户态要让 `wifid`/`corewifi`/SkyWalker 认一个 Apple HAL 表面。
  "能上网"和"设置里 WiFi 图标可用"是两个工程，后者天花板比基带还高。

### 三条线当前的性价比排序（我的判断，等用户定）
1. **②-D**：零开机抓厂商 GPR **接收**方向（可能一举定掉内容轴，且不花开机预算）。
2. **基带的内核半边**：鉴权 MSS → mpss GLINK 边 → QRTR 枚举 → 几个 QMI service。
