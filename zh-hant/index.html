把 iOS 16 的核心，
開機到一台
Redmi Note 12 Turbo

Apple 開放原始碼的 XNU（iOS 16 那一代）跑在小米這顆 Snapdragon 7+ Gen 2 上，上面是 iPhone X 的 iOS 16.7.16 使用者態：launchd、系統守護程序、backboardd、SpringBoard、內建 App。啟動鏈是自己寫的裸機 shim，從 fastboot 直接把映像檔推進記憶體跑，不刷 boot、不寫 userdata、不動分割表。

這是研究專案，不是一台能用的手機。現在能進主畫面、能觸控、能用硬體按鍵；音訊暫停在 73/120，Wi-Fi 正在施工，GPU 第二優先。缺的東西比列出來的多。

01 / 啟動鏈

四段路，沒有一段是現成的

從 fastboot 到主畫面之間原本什麼都沒有：沒有 UEFI，沒有 Linux，沒有廠商驅動。每一段要嘛自己寫，要嘛把 iPhone 的驅動搬到一顆它從沒見過的高通 SoC 上。

  1. ABL

    小米的 fastboot

    boot.img header v4（header 1584 / signature 4096）。只借它把映像檔送進記憶體；verifiedbootstate 是 orange。

  2. shim

    自寫 AArch64 裸機

    讀出硬體事實、設定 MMU 與 16 KB 頁表、把 splash 畫進 framebuffer、組裝 XNU payload，然後跳進核心。

  3. XNU

    xnu-8796.141.3，SWEET / DEVELOPMENT

    GICv3、VTIMER INTID 27、8 核心 SMP。裝置樹由 D22AP 的 .adt 加上從實機 live FDT 蒐集到的 marble 位址合成。

  4. userland

    iPhone X 的 iOS 16.7.16

    檔案系統是 userdata 尾端切出來的 HFS+ 分割區；launchd、SpringBoard、內建 App 原封不動。

搬驅動時要付的三筆學費

msr CNTP_CTL_EL0 → NOP
這顆 SoC 在 EL1 不給實體計時器，XNU 只能走 CNTV。不改就直接 Undefined kernel instruction。
GICR stride 是 0x40000，不是預設的 0x20000
marble 的 redistributor 間距 256 KB。用 cpus=1 時永遠只碰到 offset 0，所以這個差異一直藏著；要起 8 核心就必須明確傳 gicrstride=0x40000。
UFS 要往裝置 W-LUN 0xD0 發 START STOP UNIT
ABL 交接時 UFS 是斷電的，一般 LUN 的喚醒無效。cdb[4]=0x10 之後 INQ / TUR / CAP / READ / GPT 才全部成立。

03 / 時間軸

十五個節點，從一句「不可能」到 2026-11-28

日期取自倉庫提交時間戳與 GitHub Actions 的建置記錄，順序按實際發生排；docs/status-log.md 裡若干條日期在幾次轉手之後已經和當時不符，不作依據。

  1. 2026-10-21 15:58

    「紅米 Note 12 能刷 iOS 嗎？」

    得到的回答是：不可能。iOS 不開放原始碼、Secure Boot、SHSH 簽章、Secure Enclave，只認 A 系列晶片。專案是從這句「不可能」開始的。

  2. 2026-10-21

    shim 探硬體，最小根在記憶體裡

    16 KB 頁、MIDR、GICv3、framebuffer 全部實測通過。19:05 第一次 shim 上機是亂碼 + 紅藍屏，19:09 修復版拍到 P1 診斷；19:31 CI run #1 成功。23:00 panic 在 msr CNTP_CTL_EL0，NOP 之後 XNU 到 console；23:19 螢幕打出 userland alive——16 MB HFS+ 最小根由 shim 以 rd=md0 帶進記憶體，裡面只有一個靜態 /sbin/launchd，不碰 UFS。

  3. 2026-10-22

    UFS 醒過來

    ABL 交接時 UFS 是斷電的，一般 LUN 的喚醒無效；往裝置 W-LUN 0xD0 發 START STOP UNIT（cdb[4]=0x10）之後 INQ / TUR / CAP / READ / GPT 全部成功，讀出 SAMSUNG KLUEG8UHGC-B0E1、4 KiB 區塊、約 256 GB。22:53 檔案層級備份校驗完成；深夜開始把約 11 GiB 的 HFS+ 映像檔按 1 GiB × 16 塊寫進 userdata 尾端，GPT 全程沒動。同一天發現 0082 的 hunk 行號寫錯導致 CI 靜默跳過補丁——marker 門由此而來。

  4. 2026-10-23 01:05

    Apple logo + 進度條：iOS 在引導

    launchd_cache_loader 過了，launchd 已經在跑使用者態引導，不再是核心 panic 屏。02:07 日誌確認 SpringBoard(pid 26) 與 backboardd(57) 都在運行、framebuffer 交換 19.4 萬次；停在進度條的原因是缺 preboot 卷、獨立資料卷、SEP、前景工作階段、GPU 加速和基頻/藍牙守護程序。

  5. 2026-10-23 10:21 → 15:11

    進 Setup，再進桌面

    10:21「成了，進 setup 了」：繞過 datamigrator + 啟用種子這條路走對，隨後開始新寫 Goodix GT9916R over SPI 的觸控驅動。15:11「進桌面了，但是沒有壁紙，鎖屏時鐘是紅色的」：SetupDone 生效，使用者態徹底過了 Setup；壁紙與紅色時鐘歸到 WallpaperKit / 顏色管線，還沒有 GPU 合成。

  6. 2026-10-23 → 24

    音訊開工

    LPASS/WCD938x 唯讀探針 → AOP command DB → 走 TZ PAS 載入與釋放 ADSP → 最小 GLINK/GPR 用戶端 → 經 q6prm 投 LPASS。第二天打開廠商自己的 AudioReach 播放圖、灌進 1 kHz、開始碰功放 I2C，也第一次試了 HAP520 觸感引擎。

  7. 2026-10-27

    八核心是修音訊時順手修的

    marble 的 GICR 間距是 0x40000，不是 XNU 預設的 0x20000；改成執行期可設定、ADT 裡放八個核，8/8 起來。同一天記下 apps-smmu 的死路、盤了 GPU 可行性（kgsl-smmu 與 apps-smmu 是兩顆獨立 SMMU），並確認喇叭走 TERTIARY TDM + 兩顆 AW882xx，不是 WSA。

  8. 2026-10-30

    觸感反饋：輸出端解決

    AP 端用 SPMI 直接驅動 PMIC HAP520，44/44 次有震感、震感與設定一致。同一輪修掉 SpringBoard 的 TCC 當機（補上 16 個 usage 鍵）。剩下的不在硬體：UIKit / CoreHaptics 的要求被 backboardd 的使用者端 gate 擋下，這條線當天暫停。

  9. 2026-11-02

    音訊資料面打通

    門檻不是廠商那 18 KB 校正，而是 S1 末梢頁表項目的 AP 位元——DSP 非特權讀取被 SMMU 終止。改到 sweets1ap=3 之後 DATA_BUFFER done status=0 回來，1200 個 buffer 跑完並正常復位。

  10. 2026-11-03

    mediaserverd 來 open 我們的殼

    線上格式在本機 libar-gsl.so 上逐條反組譯複驗：記錄標頭 16 B、OOB 包結構、正文 ≤256 走帶內；SHM 映射的高 32 位元是 stream index 而不是位址。pid 28 呼叫了 method_Open。

  11. 2026-11-05

    一條軸關門，兩條線改道

    帶外 SET_CFG 的 E–N 十輪把位址、傳輸、長度、正文字節逐格排除；N1 的哨兵證明之前那些 err=0 其實是「沒人寫過」。同一天 Wi-Fi 決定暫緩，基頻開線先做零開機盤點。

  12. 2026-11-07

    圖的內容判死，GPU 凍結

    離線核清圖產生軸（2960 是當代四個 key，舊的 2724 屬於上一代且自身索引越界）；逐字 dump 兩次推翻「圖裡缺 DEC/CNV」，真正缺的是 PCM_DEC + PCM_CNV。856 B 的圖能開、能起、能推 120 影格，人耳三次都沒聽到；EOS_RENDERED 在收包儀器被證明活著的前提下從未抵達。GPU 線轉凍結。

  13. 2026-11-08 → 13

    修功放，然後接上 HAL

    功放兩處真實缺陷實機生效：初始化不再執行診斷復位，暫存器寫合成三位元組單則訊息，兩顆的表值 b440 / 05a9 回讀一致。11-10 重啟音訊做 capture-only HAL；第 70 輪 HAL → AudioReach 連續流 30/30/30、六條控制應答全 0——仍然不是發聲。

  14. 2026-11-14 → 15

    定位到功放沒有 TDM 時脈

    第 72 輪有效無聲：兩顆 AW88266 的 profile / ID / vol 都對，清掉 PWDN 之後 SYSST=0、PLL 全 0，安全門在任何 period 提交前拒絕並雙關斷。0297 補上廠商那張精確 PRM 票，第 73 輪判為 PRM 回包解析失配——應答是 0x02001002 配 0x0800102c，不是 BASIC_RSP；0298 已離線修好綁定。聲音仍未證明。

  15. 2026-11-20 → 28

    Wi-Fi 成為主線，GPU 轉為第二優先

    引入 FoXLinne 的 marble 參考。第 74 輪唯讀 handoff 通過，確認 QCA6490/PCIe0 交接後保持關閉；端點識別尚未驗證。0302/0303 把 109 個無線堆疊物件、韌體、DMA/SMMU 核心離線接進同一個物件，但還沒進入 XNU 的實際啟動路徑。預算仍 74/120。

04 / 踩過的坑

一個人踩不完所有的坑，所以坑要寫下來

這個專案最貴的資源不是時間，是開機次數——一次開機等於一次實機、一次取日誌、一次歸因。下面四條機制都是為了把它變便宜才長出來的。

marker 門檻：讓被跳過的補丁呈現為一次 CI 紅

每個補丁自帶一條唯一的 printf 字面值，GitHub Actions 建置完 XNU 後在產出物裡逐條 grep。補丁因為基線選錯而沒打上時，紅的是 CI，不是一次白花的開機。改一條字串必須在同一個 push 裡刪掉舊 marker。

cmdline 只有 590 位元組

啟動參數塞到 607 位元組會被截斷，而且是靜默切值：sweetbufs=30 變成 sweetbufs=3，於是就拿一個約 12 ms 的音當負讀數寫進結論。現在 mkimage.sh 在超長時直接報錯退出，不許繞過。

日誌要從磁碟尾端取，而且先對身分

核心 console 在 exec bluetoothd 之後大致是啞的，所以關鍵行直寫 ring buffer，落在 userdata 尾端，復位後用腳本拉回來。單筆記錄約 240 位元組、截斷不加分隔符，一個「長行」其實是幾條粘在一起。每輪先 grep sweettime 核對身分——對不上意味著這一輪根本沒寫 ring，而腳本會安靜地把上一輪給你。

判準表必須在開機之前 commit

一次實驗只動一個語意變數，並印出它實際用的參數；判決表在開機之前寫死，事後不改。儀器必須能自證失敗：只在已被證明會執行的路徑上列印，否則明確標註「非判準」。尺寸湊對了不算證據——同一個 u32=18504 在廠商 ACDB 裡能出現幾十次。

05 / 還差什麼

沒做到的部分，才是這份清單的意義

聲音。音訊暫停在 73/120。資料面、HAL 連續流、功放修正都已通過；最後一次有效負讀數是功放沒有 TDM 時脈。0298 已離線修好 PRM 回包綁定，尚無新核心/映像/開機。

Wi-Fi。第 74 輪唯讀 handoff 通過，確認 QCA6490/PCIe0 交接後保持關閉；端點識別尚未驗證。0302/0303 已離線整合 109 個無線堆疊物件、韌體與 DMA/SMMU 核心，但還沒進入 XNU 的實際啟動路徑。

圖形。每個像素仍是 CPU 算的。FoXLinne 的上游 iOS 18 GPU 實作可參考，但 iOS 16 適配尚未開始；舊 XNU 8796 線仍凍結。

儲存。root 映像檔位於 userdata 尾端，但 f2fs 沒有縮小、GPT 沒有改。研究機日常還要開 Android，寫滿就會覆蓋 root；目前只能開機前重讀卷頭簽章與 free 區塊數，發現被覆蓋就重新分塊寫尾端。

可用性。缺 preboot 卷、獨立資料卷、SEP、前景工作階段；部分 App 看門狗逾時；空密碼仍要求輸入（使用者態 bug）。目標不是日常手機，而是回答「Apple 的核心離開出廠校正的硬體能走多遠」。

已證偽的路線。SMMU 死路、拿 DATA_BUFFER 當探針、用 tinyplay 擾動測時脈——每一條都花過實機開機，列出來是為了省下你的。

06 / 怎麼跑一遍

你需要自備的檔案

倉庫是純程式碼、補丁與文件，不含任何 Apple、高通或小米的二進位檔。XNU 原始碼由 CI 從公開來源建置；下面三樣只能從你自己的裝置來。

需要自備的檔案
檔案來源
d22ap.adt你自己的 iPhone X（D22AP）iOS 16.7.16 IPSW。Apple 版權內容，不可再散布。
adsp2.mdt 與分段你自己手機上的 /vendor/firmware/，用 extract_adsp_fw.sh 抽取（需要 root）。
HFS+ 使用者態映像檔你自己的 iPhone X IPSW 或裝置。倉庫不提供，也不提供取得管道。

建置 → 啟動 → 取日誌，全程只 fastboot boot

# 1. 取回 CI 產出物並打上 CNTP_CTL NOP（一定要用處理過的核心）
GH_REPO=<你>/ios-port-marble ./scripts/fetch_kernel.sh

# 2. 從手機抽 ADSP 韌體
SERIAL=<你的裝置> ./scripts/extract_adsp_fw.sh

# 3. 產生純 RAM 啟動映像檔
D22AP_ADT=/path/to/d22ap.adt ADSP_FW_DIR=$PWD/adsp-fw ./scripts/mkimage.sh

# 4. 啟動。不寫任何分割區。
SERIAL=<你的裝置> ./scripts/boot_ram.sh images/shim-iosroot-adsp.img

# 5. 取回這一輪的 ring 日誌
SERIAL=<你的裝置> ./scripts/pull_logs.sh run1

只對你自己的裝置使用。測試前一定先備份原機資料——別學我不備份就在線上調整 userdata 分割區大小，這很看運氣。另外要知道怎麼進 fastboot（Power + Vol Down）和復原路徑。核心 panic 時螢幕會花，建議先拍照，再記下 pc / lr / far 然後重開。

07 / 參與

歡迎一起折騰

  • 有同款裝置（Redmi Note 12 Turbo / marble / SM7475）：幫忙實機重現、抓日誌、讀暫存器、驗證補丁。
  • 做過 XNU / IOKit / 驅動移植：補丁和程式碼審查都歡迎，一個 PR 盡量只做一件事。
  • 懂高通 PMIC / RPMh / SMMU / AudioReach：如果文件裡有錯，或者這條路你早走通過、走死過，請一定告訴我們。

開 Issue 請貼四樣：現象、logs/ring-*.txt、啟動參數、以及映像檔識別碼 sweettime。有這四樣，同一輪實驗就能重現。範圍不限於 bug——「這條路我試過，結論是 X」同樣有價值。

失敗的嘗試也請順手寫進 docs/，下一個人就不會重走。
