The iOS 16 kernel,
booted on a
Redmi Note 12 Turbo

Apple's open-source XNU — the iOS 16 generation — running on Xiaomi's Snapdragon 7+ Gen 2, with the iPhone X's iOS 16.7.16 userland on top: launchd, the system daemons, backboardd, SpringBoard, the stock apps. The boot chain is a bare-metal shim we wrote ourselves, which takes the image straight into memory from fastboot — no boot partition flashed, no userdata written, no partition table touched.

It is a research project, not a phone you can use. It reaches the home screen, the touchscreen works, the hardware buttons work. Audio is paused at 73/120, Wi-Fi is under construction, and GPU is second priority. What's missing outweighs what's listed here.

01 / Boot chain

Four stages, and none of them off the shelf

Between fastboot and the home screen there was originally nothing: no UEFI, no Linux, no vendor driver. Every stage is either written from scratch, or a driver lifted off an iPhone and dropped onto a Qualcomm SoC it has never seen.

  1. ABL

    Xiaomi's fastboot

    boot.img header v4 (header 1584 / signature 4096). Borrowed only to get the image into memory; verifiedbootstate is orange.

  2. shim

    Our own AArch64 bare metal

    Reads out the hardware, sets up the MMU and 16 KB pages, draws the splash into the framebuffer, assembles the XNU payload, then jumps into the kernel.

  3. XNU

    xnu-8796.141.3, SWEET / DEVELOPMENT

    GICv3, VTIMER INTID 27, 8-core SMP. The device tree is built from D22AP's .adt plus the marble addresses collected from the live FDT on the phone.

  4. userland

    iPhone X on iOS 16.7.16

    The root filesystem is an HFS+ partition carved off the tail of userdata; launchd, SpringBoard and the stock apps are unmodified.

Three lessons we paid for while porting drivers

msr CNTP_CTL_EL0 → NOP
This SoC does not expose the physical timer at EL1, so XNU has to run on CNTV. Leave the instruction in and you get Undefined kernel instruction.
The GICR stride is 0x40000, not the default 0x20000
marble's redistributors sit 256 KB apart. With cpus=1 you only ever touch offset 0, so the difference stayed hidden; bringing up 8 cores means passing gicrstride=0x40000 explicitly.
UFS needs START STOP UNIT on device W-LUN 0xD0
UFS is powered down when ABL hands over, and waking a normal LUN does nothing. Only after cdb[4]=0x10 do INQ / TUR / CAP / READ / GPT all succeed.

03 / Timeline

Fifteen turning points, from "impossible" to 2026-11-28

Dates come from commit timestamps in the repository and from the GitHub Actions build log, ordered by what actually happened. Several dates inside docs/status-log.md drifted during hand-offs and are not used here.

  1. 2026-10-21 15:58

    "Can a Redmi Note 12 run iOS?"

    The answer was no: iOS is closed, Secure Boot, SHSH-signed, Secure Enclave, A-series only. The project started from that "impossible".

  2. 2026-10-21

    The shim probes the hardware; the root lives in RAM

    16 KB pages, MIDR, GICv3 and the framebuffer all verified. At 19:05 the first shim boot produced garbled output and red/blue screens; at 19:09 the fixed shim's P1 diagnostics were captured. CI run #1 succeeded at 19:31. A 23:00 panic in msr CNTP_CTL_EL0 was NOPed; at 23:19 the screen printed userland alive — a 16 MB HFS+ root carried in RAM by the shim via rd=md0, containing only a static /sbin/launchd. UFS was not involved.

  3. 2026-10-22

    UFS wakes up

    UFS is powered down when ABL hands over and waking a normal LUN does nothing; after START STOP UNIT on device W-LUN 0xD0 (cdb[4]=0x10), INQ / TUR / CAP / READ / GPT all succeed and the disk reports as a SAMSUNG KLUEG8UHGC-B0E1, 4 KiB blocks, about 256 GB. At 22:53 the file-level backup passed verification; late that night an ~11 GiB HFS+ image was written into the tail of userdata in 16 × 1 GiB chunks, without touching GPT. The same day a wrong hunk line in 0082 made CI silently skip the patch — the origin of the marker gate.

  4. 2026-10-23 01:05

    Apple logo + progress bar: iOS is booting

    launchd_cache_loader passed and launchd was already running userland boot tasks, no longer a kernel panic screen. At 02:07 the log confirmed SpringBoard (pid 26) and backboardd (57) were alive with 194,000 framebuffer swaps; the progress bar waited for a preboot volume, a separate data volume, SEP, a foreground session, GPU acceleration and baseband/Bluetooth daemons.

  5. 2026-10-23 10:21 → 15:11

    Setup, then the home screen

    At 10:21: "made it into Setup" — bypassing datamigrator and walking through activation worked, and the Goodix GT9916R over SPI touch driver was written next. At 15:11: "made it to the desktop, but no wallpaper and the lock-screen clock is red" — SetupDone had taken effect. Wallpaper and the red clock were left to WallpaperKit / the color pipeline, with no GPU composition yet.

  6. 2026-10-23 → 24

    Audio starts

    Read-only LPASS/WCD938x probe → AOP command DB → loading and releasing the ADSP through the TZ PAS interface → a minimal GLINK/GPR client → voting LPASS on through q6prm. The next day the vendor's own AudioReach playback graph was open, a 1 kHz tone was feeding it, amplifier I2C was being probed, and the HAP520 haptics engine got its first try.

  7. 2026-10-27

    Eight cores, fixed as a side task during the audio push

    marble's GICR stride is 0x40000, not XNU's default 0x20000; made runtime-configurable, eight cores in the ADT, 8/8 alive. The same day recorded the apps-smmu dead ends, surveyed GPU feasibility (kgsl-smmu is a separate SMMU from apps-smmu), and confirmed the speaker is TERTIARY TDM plus two AW882xx — not WSA.

  8. 2026-10-30

    Haptics: the output side is solved

    Driving PMIC HAP520 directly over SPMI from the AP: felt 44 times out of 44, matching what was set. The same round fixed SpringBoard's TCC crash (16 usage keys added). What remains is not hardware — requests from UIKit and CoreHaptics are stopped by a user-space gate in backboardd, and the line paused that day.

  9. 2026-11-02

    The audio data plane opens

    The gate was not the vendor's 18 KB calibration but the AP bits of the S1 leaf page-table entry: unprivileged DSP reads were terminated by the SMMU. With sweets1ap=3, DATA_BUFFER done status=0 returns, 1200 buffers complete and the kernel resets normally.

  10. 2026-11-03

    mediaserverd opens our shells

    The wire format re-verified instruction by instruction against the device's own libar-gsl.so: 16-byte record header, OOB packet layout, in-band below 256 bytes; the high 32 bits of the SHM mapping are a stream index, not an address. pid 28 calls method_Open.

  11. 2026-11-05

    One axis closes, two lines change course

    Rounds E through N on out-of-band SET_CFG eliminate address, transport, length and payload bytes one cell at a time; the N1 sentinel proves the earlier err=0 readings meant "nobody wrote it". The same day Wi-Fi is parked and the baseband line starts with a zero-boot survey.

  12. 2026-11-07

    Graph content settled, GPU frozen

    The graph-generation axis closed offline (2960 is the current four keys; the old 2724 belongs to a previous generation and overruns its own index). Verbatim dumps overturned "the graph is missing DEC/CNV" twice — what is missing is PCM_DEC plus PCM_CNV. The 856 B graph opens, starts and pushes 120 frames; a human ear heard nothing on three attempts, and EOS_RENDERED never arrived even with the packet logger proven live. The GPU line goes frozen.

  13. 2026-11-08 → 13

    Fix the amplifiers, then bridge the HAL

    Two real amplifier defects fixed and verified on hardware: init no longer performs a diagnostic reset, and a register write becomes a single three-byte message — both chips read back b440 / 05a9. Audio reopened on 11-10 as a capture-only HAL; round 70 streams HAL → AudioReach 30/30/30 with all six control replies at zero. Still not sound.

  14. 2026-11-14 → 15

    Located: the amplifier has no TDM clock

    Round 72 is a valid silence: both AW88266 have the right profile / ID / volume, but after clearing PWDN, SYSST=0 and every PLL reads 0, so the safety gate refuses before any period is submitted and shuts both down. Patch 0297 adds the vendor's exact PRM clock vote; round 73 turns out to be a PRM reply parsing mismatch — the answer is 0x02001002 with 0x0800102c, not a BASIC_RSP. 0298 fixes the binding offline. Sound is still unproven.

  15. 2026-11-20 → 28

    Wi-Fi becomes the main line; GPU moves to second priority

    FoXLinne's marble port is brought in as a reference. Boot 74 passed the read-only handoff and confirmed QCA6490/PCIe0 stays powered down after ABL/TWRP handoff; endpoint identification is not verified. 0302/0303 integrate 109 wireless-stack objects, firmware and the DMA/SMMU core into one object, but it has not entered XNU's real boot path. The budget remains 74/120.

04 / Pitfalls

You can't hit every bug alone, so write the bugs down

The scarcest resource on this project isn't time, it's boots: one boot equals one device, one log pull, one attribution. The four mechanisms below exist to make that cheaper.

The marker gate: a skipped patch costs a red CI, not a wasted boot

Every patch carries one unique printf literal, and GitHub Actions greps for those literals in the built artifact. When a patch fails to apply because the baseline was wrong, CI goes red instead of you burning a boot. Change a string and the old marker has to go in the same push.

The cmdline is only 590 bytes

Push boot arguments past 607 bytes and they get truncated — silently, by cutting a value: sweetbufs=30 became sweetbufs=3, and a conclusion got written off a 12 ms tone. mkimage.sh now exits with an error when it's too long, and there is no way around it.

Logs come off the tail of the disk, and identity comes first

The kernel console goes mute after exec bluetoothd, so the important lines are written straight into a ring buffer at the tail of userdata and pulled back after the reset. A record is about 240 bytes and truncation adds no separator, so one “long line” is really several stuck together. Every round starts by grepping sweettime: if it doesn't match, that round never wrote the ring — and the script will quietly hand you the previous one.

The verdict table is committed before the boot

One semantic variable per experiment, and print the arguments actually used. The verdict table is written and committed before booting, never edited afterwards. An instrument must be able to prove it can fail: print only on a path already shown to run, otherwise mark it explicitly as not a verdict. Matching a size proves nothing — the same u32=18504 appears dozens of times in the vendor ACDB.

05 / What's missing

The parts that don't work are the point of this list

Sound. Audio is paused at 73/120. The data plane, HAL stream and amplifier fixes passed; the latest valid negative is that the amplifier has no TDM clock. 0298 fixes the PRM reply binding offline, with no new kernel, image or boot.

Wi-Fi.Boot 74 passed the read-only handoff and confirmed QCA6490/PCIe0 stays powered down after ABL/TWRP handoff; endpoint identification is not verified. 0302/0303 integrate 109 wireless-stack objects, firmware and the DMA/SMMU core, but have not entered XNU's real boot path.

Graphics.Every pixel is still computed by the CPU. FoXLinne's upstream iOS 18 GPU implementation is a reference, but the iOS 16 port has not started; the old XNU 8796 line remains frozen.

Storage.The root image lives in the tail of userdata, but f2fs was not shrunk and GPT was not changed. The research phone still runs Android, so filling userdata will overwrite the root. Today the only guard is to re-read the HFS+ header signature and free-block count before boot, then rewrite the tail if it was overwritten.

Usability.There is no preboot volume, separate data volume, SEP or foreground session; some apps hit watchdog timeouts; an empty passcode still demands input (a userland bug). The goal is not a daily phone, but to find out how far Apple's kernel gets once it leaves factory-calibrated hardware.

Routes already disproved.SMMU dead ends, using DATA_BUFFER as a probe, perturbing the clock with tinyplay — each cost a real boot, which is why they are listed: to save you the one.

06 / How to run it

Files you have to bring yourself

The repository is code, patches and documentation only — no Apple, Qualcomm or Xiaomi binaries. XNU itself is built by CI from public sources; the three things below can only come from your own devices.

Files you need to supply
FileWhere it comes from
d22ap.adtYour own iPhone X (D22AP) iOS 16.7.16 IPSW. Apple copyrighted content; it may not be redistributed.
adsp2.mdt and its sectionsFrom /vendor/firmware/ on your own phone, pulled with extract_adsp_fw.sh (needs root).
HFS+ userland imageYour own iPhone X IPSW or device. The repository does not provide it, and does not provide a way to get it.

Build → boot → pull logs, with fastboot boot only

# 1. Fetch the CI artifact and apply the CNTP_CTL NOP (use the processed kernel)
GH_REPO=<you>/ios-port-marble ./scripts/fetch_kernel.sh

# 2. Pull the ADSP firmware off the phone
SERIAL=<your-device> ./scripts/extract_adsp_fw.sh

# 3. Build the RAM-only boot image
D22AP_ADT=/path/to/d22ap.adt ADSP_FW_DIR=$PWD/adsp-fw ./scripts/mkimage.sh

# 4. Boot it. Nothing is written to any partition.
SERIAL=<your-device> ./scripts/boot_ram.sh images/shim-iosroot-adsp.img

# 5. Pull this round's ring log back
SERIAL=<your-device> ./scripts/pull_logs.sh run1

Use it on your own device only. Back the device up first — I didn't, I resized userdata in place without a backup, and whether that works out is down to luck. Know how to get into fastboot (Power + Vol Down) and where your recovery path is. When the kernel panics the screen tears: photograph it, note pc / lr / far, then reboot.

07 / Contribute

Come tinker with it

  • Own the same phone (Redmi Note 12 Turbo / marble / SM7475): reproduce on hardware, pull logs, read registers, verify patches.
  • Work in XNU / IOKit / driver porting: patches and code review are both welcome. Keep one PR to one thing.
  • Know Qualcomm PMIC / RPMh / SMMU / AudioReach: if something in the docs is wrong, or you have already walked this road to a dead end, please tell us.

In an issue, paste four things: what happened, logs/ring-*.txt, the boot arguments, and the image identity sweettime. With those four, the round is reproducible. Not only bugs — “I tried this road, the answer is X” is just as valuable.

Write the failed attempts into docs/ as well. The next person won't have to walk it twice.

Issues and pull requests in 中文 or 繁體中文 are welcome too.

Whose shoulders

The public reference projects ios-sweet (the same XNU generation ported to a Redmi Note 10 Pro / SM7150) and ios-topaz were the starting point. This project swapped the addresses, clocks, interrupts, touch and UFS over to marble's, and re-verified every SM7150 driver it inherited. Audio sources from other ports, and vendor kprobe traces, have been used to cross-check our wire format.
